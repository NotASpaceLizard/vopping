# Playbook Updates Pending

Running log of process lessons learned on **vopping** that should get folded into `AGENTIC_ORCHESTRATION_PLAYBOOK.md` at project wind-down. Not yet applied — this is a queue, not a changelog. Orchestrator-owned; add to it as things come up, don't edit the playbook itself until the PO says the project is winding down.

## Console

- **Messages tab pattern**: a curated, one-way PO-facing digest, separate from the raw Team Status activity feed. Each entry tagged `needsReply` / `answered`. Sort: unanswered-needs-reply group first, then reverse-chronological within each group. Paginated the same way as the activity feed. Built specifically because the PO described raw agent-relay narration in chat as "drinking from a firehose."
- **Discipline, not just a feature**: it's not enough to avoid narrating *agent-relay* traffic in chat — any substantive PO-facing content at all (a recommendation, a proposed resolution, an answer to their question) has to be mirrored into the Messages array in the *same turn* it's said in chat, not backfilled later. This was corrected roughly 5 times in one session on vopping before it stuck. The console can't be a trusted source of truth if real content only lands there after the PO complains it's missing.
- **Confirm the viewing model explicitly, don't assume**: ask the PO up front whether they view the console locally (`file://`, no push needed) or need it live somewhere (e.g. GitHub Pages, needs push after every edit). On vopping the PO views the console locally but views the actual app/decision-tools (e.g. a density picker) on their phone via Pages — two different files, two different sync requirements. Conflating them caused real confusion twice.

## GitHub setup

- **Check the authenticated host, not just whether `gh` is authenticated at all.** A work machine can be logged into a corporate/enterprise GitHub host while the PO's actual personal projects live on public github.com under a different account. `gh auth status` can show a host and look "logged in" while still being the wrong host entirely. Confirm which host+account the PO actually wants before creating anything.

## Decision-tool artifacts (palette-picker.html-style)

- **Scope the mockup to the whole real row/element, not just the dimension being decided.** vopping's first density-picker.html draft showed only checkbox+name+aisle-tag; QA caught that it omitted the delete/reorder/note controls that would actually share that row, meaning a PO pick made against it risked not holding once the real controls landed — same "crowded row" failure class as vacking's own MV-1/MV-3 bugs. Build the decision tool against the full realistic element from the start.
- **Reversibility framing for "future-proofing" worries**: when a PO worries about removing a visual affordance (e.g. "what if we want a checkbox back later and there's no room") — for a static HTML/CSS UI, removing a glyph is usually a reversible markup/CSS choice, not a data-model lock-in. Don't reserve hidden space for a hypothetical future need; note that reversing course later just costs the density back, symmetric either direction.

## Role boundaries

- **The Orchestrator writing a decision-tool artifact directly (not through Developer) is a real mistake, not a shortcut.** Caught on vopping when the Orchestrator wrote the first density-picker.html draft itself instead of delegating to Developer — PO corrected it immediately ("you are my orchestrator, not my developer"). The console itself remains the sole Orchestrator-owned exception; everything else, including one-off decision-tool mockups, goes through Developer.
- **Track agentId-to-role mapping explicitly; don't rely on remembering spawn order.** When Scrum Master, Developer, Tester, and QA are spawned in one parallel batch, the tool results come back in call order but nothing else labels which raw agentId belongs to which role. On vopping (after a multi-day pause forced a full re-spawn), the Orchestrator misremembered the mapping and sent a Developer-owned-file task (updating density-picker.html for a QA finding) to the Tester agent instead. Tester complied and did competent work, but it's still a role-boundary breach the Orchestrator caused, not Tester overreaching — same failure family as the Orchestrator writing density-picker.html itself. Fix: write down the role→agentId mapping as soon as the spawn batch returns (a scratch note is enough), and double-check it before every SendMessage, especially right after a re-spawn.

## Permission-chaining lesson needs more precise wording

- **Correction, not new addition — the existing playbook section on Bash chaining (§5 Layer 3) is imprecise and should be tightened at wind-down.** On 2026-09-08 the PO relayed a colleague's pushback: Claude Code isn't naively treating a whole chained command as one opaque string to prefix-match. Verified against the actual docs (code.claude.com/docs/en/permissions) and by grepping the compiled CLI binary directly for its shell-tokenizing logic: Claude Code *is* shell-operator-aware (it parses `&&`/quotes/backticks/command-substitution rather than treating the command as an opaque blob) — but that awareness means a prefix rule covering the first command does **not** automatically extend to what follows an operator, not that chaining is safely split-and-covered. Docs state it plainly: "a prefix match rule like `Bash(safe-cmd *)` won't give it permission to run the command `safe-cmd && other-cmd`." The practical guidance (one command per call, don't chain) is still correct — just needs the *why* corrected from "wildcard matching is defeated by chaining" (implies a crude bug) to "operator-aware parsing doesn't blanket-extend a single rule's coverage across chained commands" (accurate mechanism, same practical takeaway).

## Permission hygiene should be proactive, not reactive

- **Add a periodic tool-discipline reminder to the Orchestrator's own routine, not just a reactive fix after the PO notices prompts piling up.** On vopping (2026-09-08), the same two gotchas (raw Bash `grep`/`find`/`awk`/`sed` forced to "ask" by machine-wide managed-settings.json; chained `cd X && Y` defeating a simple `Bash(cd *)` allow rule) resurfaced multiple times across the session even after being fixed once — agents drift back into old habits, or a fresh agent re-spawned after a pause never got the lesson in the first place. The PO's own suggestion: build a periodic check into the process ("maybe part of our process should be a periodic reminder to use tools so that we don't wait until it's causing a problem") rather than waiting for prompts to actually start appearing before saying anything. Practical shape for the playbook: fold a one-line tool-discipline reminder (dedicated Read/Grep/Glob over raw Bash equivalents; no `cd` chaining) into every agent re-spawn/re-brief, and re-send it as a matter of course at natural checkpoints (sprint boundaries, after a multi-day pause) rather than only after the PO flags a prompt storm.

## Glyph/emoji rendering verification has a failure mode beyond tofu

- **A test browser rendering a glyph as "not tofu" doesn't mean it renders distinctly, or the same way, on the PO's actual device.** On vopping (2026-09-08), Developer verified 4 note-icon candidates (obscure "document" family codepoints, e.g. U+1F5CB/U+1F5CE) via an automated canvas pixel-comparison against a guaranteed-blank reference — a real check, and it correctly found no tofu. But when the PO looked at the pushed page on their own Windows machine, two of the candidates rendered as visually *identical* to each other (and to a third, unrelated codepoint) — not missing, just collapsed to the same generic fallback artwork, because Windows' fallback font doesn't have distinct glyphs for every codepoint in that obscure Unicode sub-block. This is a different failure mode than tofu: each glyph renders as *something*, just not the intended, distinct something. Confirmed by asking the PO to paste the actual characters they saw back into chat and checking their real codepoints via `String.codePointAt()` — a good pattern to repeat (don't trust a description of "looks like X," get the actual character and check it programmatically).
- **Practical fix — but check the project's aesthetic first:** the instinctive fix is "prefer well-established, near-universally-supported core emoji" for cross-platform rendering safety. On vopping this was almost the wrong call: the PO has an explicit preference for plain Unicode symbol/dingbat glyphs over colorful emoji-style pictographs ("i'm trying to AVOID emojis... they don't match the vibe"). Don't default to emoji as the safety fallback without checking whether the project even wants emoji at all — if not, the real fix is testing candidates *within* whatever glyph family the project does want, on the PO's actual device, not escaping to a different aesthetic to solve a rendering problem. A single test-browser screenshot is necessary but not sufficient verification for cross-platform glyph choices, regardless of which family you're choosing from.

## Orchestrator asserting a doc-status change without a confirmation report

- **Requesting a status change and receiving confirmation it landed are two different things — don't write the requested outcome into a commit message/console before the second one happens.** On vopping (2026-09-08 into 2026-09-09), the Orchestrator asked Scrum Master to flip S14/S16/S17 to Done after Tester's 180/180 independent formal pass, then the session moved on to other threads (an icon decision, a security-warning tangent, a pause request) without ever receiving Scrum Master's actual confirmation that the BACKLOG.md edit landed. The Orchestrator wrote "S14/S16/S17 formally Done (180/180)" into the end-of-session commit message and the console anyway, based on having *asked* rather than having *verified*. A fresh QA agent's routine resume re-read the next day caught the real BACKLOG.md still said "Locked" for all three — a real citation-drift bug the Orchestrator introduced, the exact category of mistake this project spent all of Sprint 1-3 training the *agents* to avoid (see the repeated "Developer's self-check numbers aren't the citation of record" pattern). The Orchestrator is not exempt from its own rule. Fix: before writing any doc-state claim into a commit message, console update, or PO-facing summary, either (a) have already received the agent's explicit confirmation that the edit landed, or (b) grep/read the actual file yourself first. "I asked for X" is not evidence X happened.

## Sibling-project review pays off

- Reviewing vacking's actual CSS/BACKLOG/QA_FINDINGS before writing a single line of vopping's own docs immediately surfaced the exact root cause of the PO's density complaint (44px checkboxes + zero row margin, a deliberate but unbalanced tap-target-comfort decision) — worth keeping as a hard requirement for any new sibling project, not just a nice-to-have.

## Device-only acceptance signals: structure the AC and the delivery around them (aisle rework, 2026-09-10)

- **When the whole point of a change is behavior only a real device can exhibit (here: iOS Safari's focus-zoom on sub-16px text inputs, and native `<select>`/`showPicker()` picker behavior), the formal pass must NOT be allowed to imply it verified that behavior.** Extending the S13 iOS lesson from "desktop/Playwright can't reproduce it" to a positive discipline the whole pipeline followed this time: the Tester's testability-check named it (NB-6), the Scrum Master folded an explicit AC line ("on-device zoom-elimination + native-picker opening are non-blocking REAL-DEVICE confirmation signals, NOT desktop-pass gates"), and the desktop formal pass asserted only *structural proxies* it genuinely can verify (the field is a native `<select>`; every new text input's computed font-size ≥16px; correct option set/order; the change-commit/migration logic; no horizontal overflow at 320/360/375/390px). Result: a clean 268/269 desktop pass that honestly doesn't overclaim, plus the real behavior routed to the PO's phone. Fold this into the playbook as the general rule for any device-/platform-specific acceptance criterion, not just iOS zoom.
- **Push the self-verified implementation to the PO's real device *in parallel with* the Tester's formal pass, don't serialize them.** The desktop formal pass and the PO's on-phone confirmation verify complementary things (logic/structure vs. actual device behavior) and neither gates the other, so pushing the self-verified build to Pages the moment it's clean — flagged to the PO as a `needsReply` "try it on your phone" item — gets the real-device signal moving while the formal pass runs. Done-flip still waits on the Tester's citation; the push is for early real-device feedback, not a Done claim (make the commit message + console say "implemented, NOT yet Done").

## The pre-Lock QA gate against real code earns its keep (R14, 2026-09-10)

- **Have QA gate the AC's *mechanism against the actual code* before Lock, not just prose coherence — it caught a C1/R13-class render-timing bug (R14) before a line was implemented.** The aisle rework moved the aisle editor off the shared text-editor infra onto a native `<select>` committing on `change`; QA traced the real `editingField`/`commitEditor`/`focusout`/`render` sequence and found that the deferred focusout-commit would `render()` away an open native picker mid-interaction (silently dropping the pick) — the same failure seam as the shipped S13 C1/R13 stale-DOM bug, in a new form the inline-editor rescue didn't cover. Catching it pre-implementation (vs. after ship, like C1) is the payoff of gating against code, not prose. Also worth carrying: the Developer's mitigation explicitly *rejected* the obvious "commit synchronously on the select's pointerdown" fix because it's the mirror image of the 2026-09-08 focusout bug (it would render away the very select being tapped) — a reminder that around this render/commit seam, the naive fix for one direction often re-creates the bug in the other; design the guard, don't just move the commit.

## Whole rework in one session — the pipeline scales to a coordinated multi-story change

- The aisle rework (5 stories, S21–S25, superseding mechanisms in 3 Done stories) went idea→shipped in a single session through the full pipeline (Developer feasibility spike → Scrum Master reshape+sanity → Developer sanity → Tester testability (0-blocking, 7 NBs) → consolidated pre-Lock fold → QA per-story gate (2 Real caught) → Developer mitigation design → SM fold → QA clean Lock-gate re-read → Lock → implement → 268/269 formal pass → Done-flips). Two things made it hold: (1) a **feasibility spike before drafting** resolved the one real technical unknown (inline-add in a native `<select>`) so the Scrum Master drafted against reality, not a guess; (2) **cross-story supersession** was handled by declaring it in the new story's AC at Lock and adding reciprocal notes to the superseded Done stories (S8/S9/S16 stay Done) — same S13→S5 / S19→S13 convention, now proven for a mechanism-level (not just UI-level) supersession with a regression-suite retrofit (222→209 by-design, not lost coverage).
