## New lessons (queue for the next fold-in)

- **After a large single-author one-pass doc rewrite, run an independent multi-lens audit before trusting it — the author is blind to exactly what a one-pass merge breaks (2026-09-21).** Folding the whole pending-lessons queue into the playbook in one Write, then asking "should QA take a pass?", was worth it: a 5-lens audit workflow (cross-ref integrity / internal contradiction / merge redundancy / cold-start actionability / source-fidelity → adversarial verify each finding → synthesize) returned "needs_correction_pass" with 9 distinct real issues. The three MEDIUM ones were all self-introduced by the fold-in and concentrated in the sections most heavily rewritten (a `style.css` classified as both a pushed Developer app-file and a "never-committed console file"; a blanket "console files are never committed" that the repo's own git state contradicts; a one-writer-invariant the `TEAM_LOG.md` row violated). The six LOW ones were cross-reference/definition/completeness gaps (renumber left "ultracode"/".permission-warmup" undefined; a lesson clause — "get the PO to pin the exact symptom first" — dropped in compression; stale "this project" attribution of a sibling-repo artifact). Takeaways: (1) the biggest risk in a one-pass fold-in is not a dropped lesson but a NEW contradiction where the fold-in's tightening collides with text elsewhere in the doc — a fresh reader catches these, the author doesn't; (2) give the audit the ORIGINAL source (here the pre-reset pending queue, passed via workflow `args`) so a fidelity lens can check nothing was lost or distorted; (3) this is the §9 workflow-tool-discipline lesson proving itself — the audit's shared CONTEXT forbade shell/web, several agents stalled-and-retried, and zero permission prompts fired the whole run.
