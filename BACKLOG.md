# Backlog

**Scope (per PO, 2026-09-04):** single-user, fully offline, self-contained webapp — used almost
exclusively on a phone, in a grocery store. This supersedes the stale top-of-file framing in
`project-notes.md`, which was written when this was conceived as a multi-user app requiring a
backend (a hard blocker at the time). That requirement is now moot: every multi-user-editing and
shareable-link requirement from `project-notes.md` has been dropped entirely, not deferred. Every
other requirement in that file's Requirements section is intact below as a real story.

**Tech stack decision (locked, 2026-09-04):** plain HTML/CSS/JS, no framework, no build step, no
backend, persistence via `localStorage` — identical architecture to sibling project vacking
(confirmed via vacking's own BACKLOG.md tech-stack decision note). Works entirely via `file://` or
a static host; no network calls of any kind are part of this app's normal operation.

**Row density — TBD, blocks nothing but affects S1/S2/S5 directly:** vacking's row density (44px
checkboxes, no row-to-row margin, ~52px/row) was too sparse for grocery use in practice — excessive
scrolling, real risk of missing an item while scanning aisles mid-shop. The Orchestrator has built
`density-picker.html` in this project's root: a real interactive side-by-side comparison of 4 row-
density options. **PO has not yet picked one.** Every story below that touches row layout (S1's
base row, S2's checkbox tap target, S5's up/down buttons) is written against a placeholder
single-line-per-item, tight-vertical-rhythm layout and explicitly flags this TBD rather than
guessing a pixel spec. See QUESTIONS.md.

**Tracked follow-up, required before S1/S2/S5 can move to Done (QA finding M3, 2026-09-04):** the
pick landing in QUESTIONS.md is not by itself sufficient closure. A CSS/markup follow-up pass
applying that pick to S1's base row, S2's checkbox, and S5's up/down buttons must actually happen
and be Tester-verified before any of those three stories' Status is flipped to Done — this note
exists specifically so that commitment doesn't silently evaporate once attention moves elsewhere,
the exact stale-status-drift shape the playbook's §6 warns about.

**Status vocabulary (controlled, do not invent new labels):** Not Started / In Progress / In
Review / Locked / Done.

**Undo scope note (applies across S6-S10, stated once here to avoid repeating it on every row):**
per PO decision, Undo is a single-last-action buffer covering exactly four mutation types — add,
check/uncheck, delete, reorder. Note edits (S7) and aisle edits (S8) are deliberately outside that
scope, not an oversight. Sorting (S9) is view-only and never touches the undo buffer at all.

## Priority Queue (initial sequencing, Scrum Master draft, 2026-09-04 — pending Orchestrator
review/relay; nothing below has started implementation yet)

**Sprint 1 — core mutable-list loop (must ship together to be usable at all):**
1. **S1** — render + single-item add + localStorage persistence (foundation everything else builds on).
2. **S2** — check/uncheck.
3. **S3** — delete (distinct from check).
4. **S4** — paste-to-ingest bulk add.
5. **S5** — reorder via up/down buttons.
6. **S6** — single-last-action undo. Sequenced **last** of the original 6 on purpose: it has a hard
   dependency on all four other mutation types (S1/S4's add, S2's check, S3's delete, S5's reorder)
   already existing to reverse.
7. **S12** (new, added 2026-09-04) — bulk "clear checked items," PO-approved resolution to QA
   finding R3. Sequenced after S6 specifically because it's undo-eligible as one atomic action
   (same precedent as S4's paste-batch) — needs the undo buffer to exist first.

**Sprint 2 — organization/enrichment on top of a working core list:**
8. **S7** — text notes per item.
9. **S8** — aisle designation (suggested + custom free text).
10. **S9** — sort view (manual/alphabetical/by-aisle). Sequenced after S8 because by-aisle sort
   needs the aisle field to exist first.
11. **S10** — "What am I missing?" frequency suggestions. Sequenced after S1 and S4 (both of
    sprint 1) because its history counter has to hook into both add paths (single-add and
    paste-ingest) from day one; also meaningfully more useful in practice now that S12 (sprint 1)
    exists to actually clear items between trips (QA finding R3).

**Unscheduled / parked (explicitly not in either sprint):**
- **S11** — recipe-paste alternate ingest mode. Low-priority future stretch only, per explicit PO
  direction not to build this now. Revisit only if asked.
