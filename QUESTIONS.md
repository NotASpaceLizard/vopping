## Blocking

| Question | Raised By | Status | Answer |
|----------|-----------|--------|--------|
| Cross-story tension flagged by QA (R2, 2026-09-04): S3 has no delete confirmation, and S6's undo is a single slot clobbered by literally any next mutating action — combined, an accidental delete can become permanent with zero warning ever shown, at any point (e.g. delete the wrong item, don't notice, check off something else before reaching for Undo — gone for good). Three concrete resolution options, so this isn't an open-ended ask: **(A, scrum-master's recommendation)** keep S3's no-blocking-confirm policy exactly as-is, but add a brief "Deleted '<item>' — Undo" toast/snackbar at the moment of deletion (in addition to the existing always-visible Undo control), so the recovery prompt appears right when it matters most instead of relying on the user remembering a static button elsewhere — lowest added friction, doesn't fully close the "did something else first" gap but meaningfully narrows it. **(B)** give delete a longer/dedicated undo window instead of sharing S6's flat single-slot rule with the other 3 action types — e.g. a delete's undo eligibility survives one additional lower-stakes action, or a short time-based window, before being clobbered — directly targets the fragility QA flagged, but breaks the current "one uniform buffer covers all 4 types identically" simplicity and adds a real special case to build/test. **(C)** add a minimal one-tap confirm specifically to individual delete only (e.g. a second tap arms-then-fires, or a small inline row affirmation) — not a blocking modal `window.confirm()` — closes the zero-warning gap completely for the highest-risk action, but partially reverses S3's original no-confirmation-on-delete decision and adds friction to the single most common destructive action in a fast in-store workflow. Blocks final AC lock on S3/S6 only — does not block Developer's sanity-check or Tester's testability-check from proceeding against today's spec in the meantime. | scrum-master (relaying QA finding R2, per Orchestrator's request for concrete options rather than an open question) | Answered | PO picked Option A, 2026-09-04, relayed via Orchestrator: a brief "Deleted '<item>' — Undo" toast at the moment of deletion, no blocking confirm — S3's no-confirm policy stays exactly as originally specified, S6's undo-buffer mechanics are unchanged; the toast is purely a UI surfacing of the existing Undo control at the moment it matters most. Folded into BACKLOG.md's S3 and S6 rows directly. |
